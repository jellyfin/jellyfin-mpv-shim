# i18n: extraction and seeding

`CLAUDE.md` carries the workflow and the one rule with real blast radius (never
`--merge`, never hand-edit a `.po`). This is the reasoning behind the tooling
choices.

## 1. Extraction is `xgettext`, not `pygettext3`

Three reasons, and the first is disqualifying on its own:

- `pygettext3` **cannot extract `msgctxt` at all** — zero contexts from a file full of
  `pgettext` calls;
- it offers GNU-vs-Solaris location *style* rather than location *granularity*;
- it marks no format strings.

## 2. References are `--add-location=file`, not line

A line number meant that every string added above another rewrote all of them, which
was **87% of a 17k-line sweep**. Adding one string mid-file now costs ~430 lines
across the 86 locales instead of ~17,000.

## 3. `regen_pot.sh` uses `find`, not a glob

It `find`s every `.py` under `jellyfin_mpv_shim/` rather than globbing. It used to use
`**`, which without `shopt -s globstar` expands like `*` — so nested packages
(`mpvtk_browser/pages`, `/settings`, `/components`, `/gateway`) were never scanned and
**~150 strings silently could not be translated**.

## 4. Why `--merge` is a maintainer operation, not part of a feature branch

The `.pot` is the template Weblate reads to discover new strings; filling the 86 `.po`
files in is Weblate's job.

Merging locally rewrites every locale — msgmerge rewrites line references and re-wraps
whatever it touches — which is ~10k lines across 86 files **even when no translation
changed**. Weblate lands real translations on `master` continuously, so that churn
collides with `master` in files nobody on the branch edited, and the conflicts are
unreadable because the diff is almost entirely reference comments.

`--merge` has to be committed and merged within the hour to be worth anything.

There is a `weblate` remote pointing at Weblate's git export; `MASTER_REF=weblate/master`
merges against the freshest volunteer work rather than whatever `origin/master` last
took.

## 5. Seeding from jellyfin-web

`./seed_from_jellyfin_web.py --web-src <checkout>` fills *untranslated* entries from
jellyfin-web's translations. This is legitimate — jellyfin-web is GPL-2.0-or-later and
this project is GPL-3.0 — and worth ~6,900 entries, because a quarter of our strings
are word-for-word theirs.

**What it writes ships.** The guards are the ones review would apply — identical
English, the same client UI, jellyfin-web's own translators agreeing on the wording in
that language, placeholders intact — so holding the result back buys a second opinion
about our screen and costs the string, in every language, until somebody gives one.
Nobody was giving one: the flag-everything era left ~6,900 entries fuzzy and shipping
nothing. `--fuzzy` restores it if a particular sweep warrants it.

A re-run also **promotes** what earlier runs left fuzzy, but only where it re-derives
the identical value from the key the entry records — so an entry a volunteer edited and
left fuzzy is left exactly as they left it, and one jellyfin-web has since reworded is
reported as `diverged` rather than quietly updated.

**A sweep can move the note off the string it described.** When a source string is
reworded, msgmerge attaches its old translation to the new msgid, marks it fuzzy, and
carries the translator comments across — our `# seeded from jellyfin-web:` line
included. The note then credits a key whose English we no longer use, and promotion
would re-derive that key's value, find it unchanged and clear the flag: `Blend Frames`
shipping the translation of `Dropped frames`, `Reasons` that of `Seasons`. So the key's
English has to still equal our msgid before the note is trusted at all
(`marker_is_current`); a note that fails that is not ours, and the entry goes back to
being an ordinary fuzzy entry nobody may touch. The August 2026 sweep reported 2,428 of
them, half of which it had just created.

Each seed carries a `# seeded from jellyfin-web: <Key>` translator comment, which is
both the provenance and the **only durable place for the mapping**: the `.pot` is
regenerated wholesale by xgettext, so a label written there dies on the next
`regen_pot.sh`. It is also what makes promotion possible at all — it is the one thing
distinguishing our seed from a volunteer's work.

**Placeholders are compared in jellyfin-web's notation.** gettext keys on the English
exactly, so our `"%d episodes"` did not match their `"{0} episodes"` and strings we had
taken from them word for word could not be seeded in any language. Matching converts
ours to `{0}` form and seeding converts their translation back, giving each `{i}` the
conversion our own msgid spends on that argument. A translation that **reorders**
positional arguments is skipped: `%s` is filled from a tuple in occurrence order, so a
swap would format cleanly, read perfectly, and name the wrong thing. Named conversions
(`%(from)d`) carry their own identity and may move freely. See
`tests/test_seed_from_web.py`.

**Seed last, and merge before sweeping again.** `--merge` treats master's `.po` as the
definition and ours as a compendium, so an entry master holds as fuzzy-with-a-value
wins and the seed is silently reverted.

## 6. `_p(context, string)` — one word, two meanings

gettext keys on the English, so a string reused in two senses collapses to one entry
and no language can tell them apart.

A context is **part of the key**, so adding one to a string that did not need it
discards every existing translation of it. Only do it where the senses genuinely
differ.

The known cases in this codebase, each confirmed against jellyfin-web needing separate
keys for the same pair:

| string | the two senses |
|---|---|
| `Record` | picker label vs button verb |
| `Channels` | picker label vs Live TV tab |
| `Download` | button verb vs dialog heading |
| `None` | no track vs no home section — a gender-agreement problem in Italian |

## 7. Which language the app runs in

Two ways it is decided, and only one of them existed before 3.1.0.

**`conf.lang` is an explicit answer** — a locale directory name (`de`, `pt_BR`,
`zh_Hans`) — and it is now the first row on the Settings landing page rather
than something only a hand-edited conf.json could reach. It is in
`RESTART_REQUIRED`: 22 module-scope `_()` / `_p()` call sites evaluate at
import, so re-running `configure()` would leave those in the old language while
everything else repainted into the new one.

**With no answer, `i18n.configure()` hands the question to gettext** — which
reads `LANGUAGE`, `LC_ALL`, `LC_MESSAGES` and `LANG`, in that order, and needs
no generated locale. `locale.getdefaultlocale()` used to answer for every
platform, and on Linux that was wrong three ways, each measured:

| fault | effect |
|---|---|
| `LANGUAGE` ignored | KDE puts the display language there (`kcm_regionandlang`) and leaves `LANG` to formats, so changing it did nothing at all |
| `LANG` needs a *generated* locale | `LANG=de_DE.UTF-8` answers `('C','UTF-8')` where only `en_US` exists — the Debian, container and Flatpak default |
| deprecated, removed in Python 3.15 | it stops working rather than degrading |

**The shipped Flatpak had both faults at once**: its sandbox has `C`, `POSIX`
and twenty English locales and nothing else, so `LANG` resolved to `C` and
`LANGUAGE` was ignored — the UI was English whatever the user asked for.
Flatpak *does* forward `LANGUAGE` in, so that was ours, not the sandbox's.
This is the likeliest reason the translations sat where they did: a large share
of users could never see their own language, so nobody was moved to finish it.

**The picker's list is generated**, by `tools/gen_locale_index.py` into
`jellyfin_mpv_shim/locale_index.py`, and refreshed by `gen_pkg.sh` next to the
`.mo` compile. It carries an endonym and a completeness percentage per locale.
Both parts are deliberate: `.po` files are not shipped, so completeness cannot
be computed at runtime; and 41 of the 86 locales sit between 25% and 50% (the
jellyfin-web seed line), so any threshold either hides most of the list or
means nothing. Listing everything with its number is the honest form, and it
shows a would-be translator where the gaps are.

A locale with no endonym in that tool's table is **not listed at all**, which
`tests/test_interface_language.py` fails on — so a language Weblate adds is
caught rather than silently unofferable.

### 7.1 Windows asks the OS

**Windows is the one platform that needs an API call.** It sets none of those
four variables, *and* it keeps the display language apart from the regional
format as two independent settings. `_preferred_ui_tags()` asks
`GetUserPreferredUILanguages` through ctypes and `_catalog_names()` widens each
BCP-47 tag into directory names.

`locale.getdefaultlocale()` was reading the wrong one of the two settings.
Measured on the Windows VM with the regional format set to German and the
display language left English:

| call | answer |
|---|---|
| `locale.getdefaultlocale()` | `de_DE` |
| `GetUserDefaultUILanguage` | `en_US` |
| `_system_languages()` | `['en_US', 'en']` |

That is the same format-versus-display split as the `LANGUAGE` row above,
landing on the same wrong half. A user in Germany running English Windows got
a German UI.

**Neither documented replacement answers this question**, which is worth
knowing before someone migrates it back. The deprecation notice points at
`setlocale()`, `getlocale()` and `getencoding()`; on Windows `getlocale()`
answers `('English_United States', '1252')`, which matches no catalog, and it
needs a `setlocale()` call this app deliberately never makes
(`mpvtk_browser/timefmt.py` says why). `locale.windows_locale` looks like the
missing piece but has no stdlib caller on any modern Windows: `locale.py`
reaches it only when the C helper returns a hex language id, which is the
Windows 95 path.

**The tags are widened by us, not by gettext**, which splits a code on its
first underscore only and would skip `zh_Hans`. `_catalog_names()` carries
that. And the preference *list* is deliberate: Mercurial and MComix both use
the single `GetUserDefaultUILanguage`, which is one language and drops the
script subtag that separates `zh_Hans` from `zh_Hant`.

**An environment variable still wins.** If any of the four is set, detection
returns None and gettext's own lookup runs, so a wrapper script or a
configured shell keeps working. Mercurial gates the same way.

**macOS has the same gap and deliberately no answer here.** It keeps the
display language in `AppleLanguages` under the global defaults domain, not in
an environment variable, so a bundle launched from Finder detects nothing —
launched from a terminal it inherits the shell's. Nobody on the project can
test macOS, so `lang` is load-bearing there rather than an untested platform
path, and this is the site if that changes.

## 8. A translation that crashes the app is dropped at build time

Four locales ship one today, and until 3.1.0 nothing noticed: `msgfmt` exits 0,
the entry lands in the `.mo`, and gettext hands it back to be formatted and
raise.

| locale | msgstr | raises |
|---|---|---|
| `ar` | `صفحة %(page)d من %(total)ات` | `ValueError: unsupported format character` |
| `gl` | `Páxina %(page) de %(total)` | `ValueError: incomplete format` |
| `ms` | `Halaman %(page) daripada %(total)` | `ValueError: incomplete format` |
| `sk` | `Používateľ {0} sa pripojil` | `TypeError` — braces for a `%s` msgid |

`Page %(page)d of %(total)d` is the reader's bottom bar, so in Galician, Malay
and Arabic the reader raised **on every repaint**.

**Filter, do not gate** ([iw]). `tools/po_lint.py` marks the offending entry
`#, fuzzy`, which does both jobs with no new mechanism: Weblate shows a fuzzy
entry as "Needs editing" so it reaches a translator, and **both compilers
already exclude fuzzy** (`tools/msgfmt.py` emits only non-fuzzy entries; GNU
`msgfmt` needs an opt-in `-f`). gettext then returns the msgid, so that one
string falls back to English and the rest of the locale is untouched. Failing
the build instead would hand a volunteer a way to break a release, and would
mean editing `.po` files by hand — which is §4's whole point.

It runs in two places, deliberately:

- **`regen_pot.sh`** writes the flag into the real `.po` files. That is the one
  thing in this repo that touches them, and it is a bounded exception to §4
  rather than a hole in it: five lines across four files, against ~10k lines
  across 86 for a `--merge`.
- **`gen_pkg.sh`'s `compile_po`** filters a throwaway copy before either
  compiler sees it, because a broken translation arrives on Weblate's schedule
  and not on ours. In front of **both** compilers, since covering only the path
  the build machine happens to take is this repo's recurring defect shape.

**It formats rather than diffing placeholder sets**, and that is what makes it
usable: the `ru` entry `{0: 0.1f}` reads like a typo and is perfectly valid — a
space is a format-spec flag — and a placeholder diff also trips on a literal
`%` in "100% on X11" and on a stray brace in prose. It honours xgettext's own
`no-python-format` flag for the same reason, and it never blames a translation
for a msgid the synthesised arguments cannot format either, so a gap can only
miss a bad entry and never drop a good one.

`tests/test_po_lint.py` tests **the filter, not the catalogs** — asserting the
shipped catalogs are clean would fail the day a volunteer types a bad
placeholder, which is inevitable and not a defect here.
